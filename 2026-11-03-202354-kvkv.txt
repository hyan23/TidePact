  从你的回答推出来的几条结论

  ① merge 按 server_seq 严格顺序执行，不能跳着处理。
  - 因为按全局顺序，本地 push 过的分支一定是服务端历史的一个前缀。
  - 所以「local_version >= version
    该忽略」只会出现在一种情况：这个事务就是我自己 push 上去、被 accept
    的那个。这样的事务整体都是自己的，不会出现部分 key 忽略、部分 key merge
    的情况。第 3 条成立。
  - 我建议服务端在每个事务上记下来源 push_id。pull 下来时，客户端直接按 push_id
    认出自己的事务并跳过，不用逐个 key 比版本。比版本的逻辑我保留，作为校验用。

  ② 有一种边界情况：push 已经被服务端 accept，但客户端崩了，没来得及写 pushed
  日志。
  - 这时 pull 会拉到自己的这个事务，而本地那条分支在日志里还是「没 push
    过」的状态。
  - 按规则这条分支不 merge，先重试 push。因为 push_id
    幂等，服务端会返回原来的结果，客户端写下 pushed 日志，然后接着 merge。
  - 所以 merge 时遇到「没 push 过的分支」，就先把未完成的 push
    做完再往下走。这个顺序是自洽的。

  ③ pull 和 merge 拆成两个后台任务，各用各的游标。
  - pull：从服务端拉取事务，原样存进本地的收件表，然后写 pulled 日志，记录
    pulled_seq。
  - merge：从收件表里按 seq 顺序取事务，一个服务端事务对应一个本地 SQLite
    事务，记录 merged_seq。
  - 两个游标满足 merged_seq ≤ pulled_seq。崩溃后各自从自己的游标接着做。

  ④ 第 5 条：k1 删除、k2 重建这种情况自然就处理对了。
  - merge 先处理到 k1 的删除，本地就标记删除。
  - k1 上本地还没 push 的修改，push 时因为 key_id 不一致而冲突。
  - 后面再 merge 到 k2 的创建，直接接进来。

  需要确认的点

  1. 第 4 条「未 push 先不 merge」的范围
     - 服务端事务 T 改了 A 和 B。本地 A 有没 push 的分支，B 没有。
     - 我的理解是：整个 T 都要等 A 的 push 结果出来才能 merge。按①，T
       后面的所有事务也跟着被卡住。
     - A 的 push 结果出来后，要么是自己的事务，跳过；要么冲突，A 分叉。这之后 T
       才整体 merge 进来。对吗？
  2. 冲突后从哪个点分叉
     - 「从最后一次 push 成功的点分叉」，这个点是否也包括 merge
       进来的节点？我的理解是「最新有效节点」，也就是 push 和 merge 都算。
     - 如果只算 push：冲突以后在 A 上的新修改，会基于一个已经过时的版本。下次
       push 又会冲突，等于白改。
     - 还有一个活锁的可能：A 冲突之后、merge 完成之前，用户又改了
       A。这个新修改又成了「没 push 的分支」，merge 再次被卡住，push
       又会冲突，可能一直循环下去。
     - 建议：冲突之后，A 上的新修改先挂起，等对应的服务端事务 merge
       完成，再以新的最新有效节点为基础。或者在冲突分支上允许 merge
       继续推进。你倾向哪种？

  - 本地有两个事务：T1 删除 A（k1），T2 重建 A（k3）。两个事务在同一次 push 里。
  - 服务端那边，A 已经被别人删掉了。

  - T2：服务端判「增」，服务端没有 A，所以 accept。

  可是按名字传染，T2 应该随 T1 一起冲突。也就是说，客户端认为 T2

  1. 写接口：显式的增/改，还是统一的 Put？

  push 时，「增」和「改」的判定规则不一样，所以每个节点都必须带上明确的操作类型
  。应用层可以选两种接口：

  - (a) 显式 Create / Update / Delete：本地已有这个 key 时，Create
    报错；本地没有这个 key 时，Update 或 Delete 报错。
  - (b) Put / Delete：Put 由存储层自动判断。本地没有这个
    key，或者已经删除，就当作「增」，分配新的 key_id；否则当作「改」。Delete
    一个不存在的 key，什么也不做。

  我倾向 (b)，应用层不用自己先查一遍。你倾向哪种？

  2. 同一个事务里多次写同一个 key

  比如一个事务里先把 A 改成 1，再改成 2。这个事务产生几个节点？

  - 合并成一个节点：A 只前进一个版本，节点的值是 2。
  - 每次写一个节点：A 前进两个版本。

  我倾向合并成一个节点：事务是原子的，中间状态对外不可见，留着没有意义。

  例外是先删除再重建：两个操作属于不同的
  key_id，必须保留成两个节点，旧链上一个删除节点，新链上一个首节点。

  这样可以吗？

  3. 事务就是一个写批次？

  传染规则只看写集合，所以我的理解是：事务就是一组原子提交的写，不记录读集合，也
  不做读校验。

  - 事务里读一个 key，能读到本事务前面写入的值。
  - 读事务外的 key，就是普通的本地读。提交时不检查这个值有没有被别人改过。

  对吗？

  1. 接口形式

    - 增：要求这个 key 当前不存在，或者已经被删除。

    重新提交。

  key_id 加 version，只带版本号不够。

  对吗？

  2. 分叉后版本号会重复，只校验版本号会出错

  冲突后会从最新有效节点分叉，新分支的版本号和冲突分支会重叠。下面这个流程里，一
  次过期的写会被误判为合法：

  1. 本地 A（k1）的有效节点是 v4。
  2. 应用 X 读到 A，拿到 (k1, v4)；接着提交了一次修改，产生 v5。
  3. 应用 Y 读到 A，拿到 (k1, v5)，然后去做别的事。
  4. push 冲突。v5 成了冲突分支，A 回到 v4。
  5. 应用 X 重新读到 (k1, v4)，再次修改 A，产生新分支上的 v5'。
  6. 应用 Y 回来，拿着 (k1, v5) 提交修改。本地当前节点也是 (k1, v5)，校验通过。

  可是应用 Y 读到的其实是已经冲突作废的 v5，这次提交本该失败。

  - (a) 每个节点再带一个本地唯一的节点 id，比如本地自增序号，写操作带它做校验。
  - (b) 分叉后版本号不复用：新分支从「冲突分支最大版本 +
    1」接着编号。比如上例中新分支直接从 v6 开始。push
    的规则改成：第一个服务端没有的节点，它的父节点版本等于服务端当前版本。

  我倾向 (a)：版本号的语义保持不变，push 规则也不用动。你倾向哪种？

  - (b) 「增」也带 token：Get 读到一个已删除的 key，返回删除节点的

❯ 解决客户端被复制的问题：

  如何客户端db被复制，就会出现两个客户端带同一个client_id
  这样push会出问题
  我希望每次push都带prev_push_id和push_id服务端存起来
  而且服务端要校验req.prev_push_id是否等于服务端的push_id，或者req.prev_push_id

  因为如果db被复制后，它们将产生完全不一样的pushid，先push的会胜利，后push的我

⏺ 我理解这个方案是在每个客户端的 push 上建一条链。服务端为每个 client_id
  保存最后一次 push 的 (prev_push_id,
  push_id)，再加上它的结果。收到请求时按三种情况处理：

  ┌──────────────────────────────────┬──────────────────────────────────────┐
  │               请求               │                 判定                 │
  ├──────────────────────────────────┼──────────────────────────────────────┤
  │ req.prev_push_id ==              │ 新的 push，链往前推进一格，保存新的  │
  │ server.push_id                   │ (prev, push_id) 和结果               │
  ├──────────────────────────────────┼──────────────────────────────────────┤
  │ req.prev_push_id ==              │                                      │
  │ server.prev_push_id 且           │ 重试，原样返回保存的结果             │
  │ req.push_id == server.push_id    │                                      │
  ├──────────────────────────────────┼──────────────────────────────────────┤
  │ 其他                             │ 链分叉了，永久拒绝                   │
  └──────────────────────────────────┴──────────────────────────────────────┘

  - 第一次 push：prev_push_id
    为空。服务端新激活的客户端，记录也是空的，满足第一种情况。
  - 本地要多存一个字段：写 prepare 日志时，把上一次 pushed 的 push_id 作为
    prev_push_id 一起存下来，之后每次重试都原样带上。

  几种复制的时机都推演过了，结果都对：

  - 在两次 push 之间复制：两份 db 的 prev_push_id 相同，但各自生成的 push_id
    不同。先到服务端的那份推进了链，后到的那份 prev_push_id
    已经对不上，永久失败。
  - 在 prepare 之后、pushed 之前复制：两份 db 带着同一个 push_id，push
    的内容也一样，因为是 prepare
    时冻结的。两份都会被当成重试，拿到同一个结果，没有问题。之后两份各自生成新的
    push_id，就回到上一种情况，只有一份能胜出。
  - 从旧的备份恢复：服务端的链已经比备份走得远了，备份带的 prev_push_id
    对不上，同样会永久失败。我认为这是对的：备份不知道服务端已经接受了哪些它自己
    push 过的事务，再继续 push 就会出错。

  接口用法：Get 返回带 token（即节点 id）的值。写入是 c.Commit(ctx, Create(k,
  v), Update(k, token, v), Delete(k, token))，所有操作在一个事务里原子提交。

  测试覆盖的场景：
  - 本地写入和 token 校验
  - 冲突后合并对方的值
  - 按名字传染，包括 push 进行中写入的事务
  - 服务端在同一次 push 内传染（先删后建的情况）
  - 响应丢失后用同一个 push_id 重试
  - 服务端剪裁后的全量 pull，包括删除、换 key_id、版本跳跃
  - db 被复制后的分叉检测，包括在 prepare 之后复制
  - 分叉后版本号重复时 token 能正确识别
  - 本地剪裁
  - 激活失败后重新注册

  讨论中没定、我自己做的决定

  - 通信用 HTTP/JSON：之前提过 gRPC，但 HTTP/JSON 不需要 protoc
    代码生成，实现更简单。要换的话只涉及 Transport 接口的实现。
  - merge 先比版本、再判断是否阻塞：本地已经有这个版本时直接忽略，即使这条
    key_id 上还有没 push 的节点也不阻塞。否则，自己被 accept
    的事务被拉回来时，会被后续的新修改反复卡住。只有服务端版本更新、本地又有没
    push 的节点时，才先 push。
  - 一次 Sync 最多连续 push 两次：第一次完成上次没完成的 prepared push，第二次
    push 它后面新积累的事务。测试里发现只 push 一次的话，这些新事务要等到下一次
    Sync 才会发出去。
  - 事务内多次写同一个 key 时的 token：都带事务开始前读到的那个 token。key
    是在同一事务里刚创建的，就带 0。

  还没覆盖的

  - 服务端没有单独的单元测试，只通过客户端的集成测试间接覆盖。
  - 后台定时同步（StartBackgroundSync）没有专门的测试。

❯ token是什么

⏺ token 就是你读到的那个节点在本地的
  node_id。写的时候带上它，用来证明「我是基于这个节点改的」。

  为什么需要它

  我们讨论时定了：写操作要带版本号，校验读到的东西没过时。但单靠 (key_id,
  version) 不够，因为冲突后会分叉，版本号会重复：

  1. 本地 A 的有效节点是 v0。应用改了一次，产生 v1，这个 v1 后来 push 冲突了。
  2. 冲突后，A 从 v0 重新分叉，再改一次，又产生一个 v1。
  3. 两个 v1 的 key_id 和版本号完全一样，但其实是两个不同的节点。

  node_id 在本地唯一，每个节点都不一样，所以能精确区分。这就是当时选的方案
  (a)，用节点 id 做校验。测试 TestStaleTokenAcrossConflictFork
  验证的就是这个场景。

  怎么用

  it, _ := c.Get(ctx, "a")  // it.Token 就是当前可见节点的 node_id
  c.Commit(ctx, client.Update("a", it.Token, []byte("new")))

  Commit 时，Update 和 Delete 带的 token 必须等于这个 key 当前可见节点的
  id，否则返回 ErrStale，整个事务失败。应用层重新 Get，再重新提交。Create 不带
  token，只检查 key 当前不存在。

  什么时候 token 会失效

  只要可见节点变了，旧 token 就失效：

  - 本地别处写过这个 key：产生了新节点。
  - merge 进了服务端的新版本：可见节点前移。
  - push 冲突：可见节点回退到有效节点，冲突分支上的节点 id 再也对不上。
  - 全量 pull 跳了版本，或者产生了本地删除节点：可见节点变了。

  push 被 accept 时，节点 id 不变，token 依然有效。

  关于名字

  叫它 token，是因为对应用层来说它是个不透明的凭证，只需要原样传回来，不用理解里
  面是什么。你觉得叫 NodeID 更直白的话，我可以改名。
