# TidePact 设计

异步多客户端、单服务端的 KV 数据库。客户端本地读写，后台与服务端同步；
一组修改作为事务原子写入本地，并原子地被服务端接受或冲突。

> 分层（上层覆盖/屏蔽底层）尚未设计，见文末。

## 1. 本地存储

- 存储为 SQLite（WAL，`synchronous=FULL`）。逻辑上是只追加日志：节点只插入，只在剪裁时删除。
- 每个 key 名对应若干条版本链。每次「增」分配一个新的 `key_id`（UUID），链从 `version=0` 开始。
- 每个节点有本地唯一的 `node_id`，用于精确识别分支。

### 写

- `Get(key)` 返回 `(key_id, version, token=node_id, value)`。
- 写操作：
  - `Create(key, value)`：要求 key 当前不存在（含已删除）。不带 token，ABA 视为正确。
  - `Update(key, token, value)`、`Delete(key, token)`：token 必须等于当前可见节点。
- 一次 `Commit` 是一个事务，所有操作原子写入；任一校验失败则整个事务失败。
- 同一事务内多次写同一 key 合并为一个节点。删除后重建属于不同 `key_id`，保留为两个节点。写入相同的值也生成新节点。
- 事务不记录读集合。应用层对读到的 key 都写一次（值不变也写），依赖由写集合表达。

### 读

1. 有未 push 的分支（含 push 中），读它的末端。
2. 否则读最新有效节点（push 被 accept 的节点，或 merge 进来的节点）。
3. 冲突分支对读不可见。

不变量：每个 key 名任何时刻最多只有一条可追加的活分支。

## 2. 注册

1. 服务端创建 `client_id`。
2. 客户端创建本地空日志。
3. 客户端调用激活（幂等）。

- 激活成功之前不能写。
- 激活失败（`client_id` 已被清理）就重新走一遍注册流程。
- 服务端定期清理一直未激活的 `client_id`。已激活的客户端永不过期。

## 3. Push

1. 写 `prepare` 日志：生成 `push_id`，记录 `prev_push_id`（上一次 pushed 的 `push_id`），冻结所有未 push 的事务。
2. 发送；用同一个 `push_id` 重试，直到成功。
3. 原子写 `pushed` 日志，同时处理 accept 和冲突。

### 服务端判定

服务端为每个客户端保存最后一次 push 的 `(prev_push_id, push_id, 完整结果)`。

| 请求 | 处理 |
|---|---|
| `req.prev == server.push_id` | 新 push |
| `req.prev == server.prev` 且 `req.push == server.push` | 重试，原样返回结果 |
| 其他 | 分叉（db 被复制或从备份恢复），永久拒绝 |

每个事务按顺序判定，整体 accept 或整体冲突：

- 增：服务端没有该 key 名（或已删除）就 accept，不比较 `key_id`。
- 改、删：`key_id` 相同，且「服务端没有的第一个版本 = 服务端版本 + 1」。
- 同一次 push 里，事务若涉及已冲突的 key 名，直接判冲突（按名字传染）。
- accept 的事务分配全局递增的 `server_seq`，并返回给客户端。

### 客户端处理结果

- accept 的事务：节点成为有效节点，记录 `server_seq`。
- 冲突的事务：在事务每个 key 的最后节点后追加冲突节点。
- 传染：push 期间新产生的事务，只要涉及已冲突的 key 名就判冲突；它涉及的其他 key 名也加入冲突集合，继续往后传。
- 冲突的 key 以后从最新有效节点分叉；没有有效节点就建立首节点（新 `key_id`）。
- 收到分叉错误：客户端标记作废，之后拒绝写、push、pull。

## 4. Pull 与 Merge

两者都在后台执行。

- **pull**：按 `server_seq` 增量拉取，存入收件箱，记录 `pulled`。
  - 新客户端，或者游标所指的日志已被服务端剪裁：改为全量 pull，拉取快照（只有叶子节点，带快照 seq `S`）。
- **merge**：按 seq 严格顺序处理，每个服务端事务原子执行。对每个节点：
  - 本地没有该 `key_id`：直接 merge。
  - 本地有：比较最新有效版本。`local_version >= version` 就忽略。否则，如果该 `key_id` 上有未 push 的节点，先 push（merge 阻塞，一直重试即可）；没有就 merge。
- **快照 merge**（整体原子）：
  1. 先删除：本地已同步、有效节点 seq ≤ `S`、且快照里没有该 `key_id` 的 key，追加本地删除节点（不 push）。
  2. 再 merge 快照，允许版本跳跃。

## 5. 剪裁

### 服务端

只保留：

- 每个存活 key 的叶子节点（增、改）。
- 每个客户端的 push 进度及其结果。

删除节点不保留。push 不受影响；pull 游标若落在剪裁范围内，就需要全量 pull。

### 客户端

- 未 push 的节点全部保留，连同它们回溯到第一个有效节点的祖先。
- 每个 key 的最新有效节点保留，但删除节点不保留（本地删除节点同样处理）。
- 冲突分支：从叶子往前保留到分叉点（第一个有效节点，push 或 merge 的都算）；没有分叉点就保留整条链。
- 同步记录（pushed、pulled、merged）各保留最后一条。
